# ATW Meta

This skill is for local ATW users who have already run `atw init` in a project. After reading it, an AI should understand the ATW architecture, operating model, and customization entry points inside that user project, then modify the generated `.atw/` and platform directory files according to the user's request.

Beyond the workflow / persistence / platform model, ATW has three further architectural surfaces. First, a multi-agent collaboration runtime: `atw channel` coordinates multiple AI worker processes through project-scoped JSONL event logs at `~/.atw/channels/<project>/<channel>/events.jsonl`, with worker OOM guard, forum/thread channels, durable idempotency keys, and bundled `.atw/agents/{review,implement-agent}.md` runtime definitions. Second, cross-session memory: `atw mem list | search | context | extract | projects` reads raw Claude Code, Codex, and Pi Agent JSONL already on disk, slices by `--phase brainstorm|implement|all`, and never uploads anything. Third, a dual-package npm release: `@chinhae/atw-cli` (CLI) and `@chinhae/atw-core` (SDK with `/channel`, `/task`, `/mem`, `/testing` subpaths) ship in lockstep on one version. Treat these as first-class customization surfaces alongside the per-platform integration files.

The default operating scope is local files in the user project:

- `.atw/`: workflow, config, tasks, spec, workspace, scripts, bundled runtime agents, and runtime state.
- Platform directories: `.claude/`, `.codex/`, `.cursor/`, `.opencode/`, `.kiro/`, `.gemini/`, `.qoder/`, `.codebuddy/`, `.github/`, `.factory/`, `.pi/`, `.reasonix/`, `.kilocode/`, `.agent/`, `.devin/`, `.kimi-code/`, and similar directories. Pi additionally exposes a native `atw_subagent` tool with `single` / `parallel` / `chain` dispatch modes, throttled progress cards, and `isAtwAgent()` validation on top of the file layout. Reasonix stores both workflow skills and subagent skills as `.reasonix/skills/<name>/SKILL.md`; subagent skills carry `runAs: subagent` frontmatter. Kimi Code keeps workflow skills in the shared `.agents/skills/` layer, delivers commands plus agent prompts as `.kimi-code/skills/<name>/SKILL.md`, and installs the same agent prompts as custom sub-agents under `.kimi-code/agents/<name>.md`.
- Shared skill layer: `.agents/skills/`.
- User-owned channel store outside the project tree: `~/.atw/channels/<project>/<channel>/events.jsonl`.
- Raw platform conversation logs queryable via `atw mem`: `~/.claude/projects/`, `~/.codex/sessions/`, and `~/.pi/agent/sessions/`, plus OpenCode's SQLite session store under its XDG data directory.

Do not assume the user has the ATW source repository. Do not default to modifying the global npm install directory or `node_modules` — both `@chinhae/atw-cli` and `@chinhae/atw-core` ship as published packages sharing one version and one git tag per release.

## How To Use

1. Read `references/local-architecture/overview.md` first to establish the local ATW system model.
2. If the request involves a specific AI tool, read `references/platform-files/platform-map.md` and the relevant platform file notes.
3. If the request involves multi-agent dispatch or channel workers, read `references/local-architecture/multi-agent-channel.md` and the bundled `.atw/agents/` files.
4. If the user wants to change behavior, read `references/customize-local/overview.md`, then open the specific customization topic.
5. Before editing, read the actual files in the user project and treat local content as authoritative.

## Current Rules

- `.atw/workflow.md` is the local workflow source of truth; its initial content was selected from a workflow template (built-in `native`, or a marketplace template — `atw workflow --list` is the only authority on what is actually fetchable) at `atw init` time and can be re-selected via `atw workflow --template <id>`. Missing `.atw/agents/<name>.md` files referenced by the active template trigger a non-blocking stderr warning pointing at `atw update`.
- `.atw/config.yaml` is the project-level ATW configuration entry point. It hosts task lifecycle hooks (`hooks.after_create` / `after_start` / `after_finish` / `after_archive`), journal shape (`session_commit_message` / `max_journal_lines` / `session_auto_commit`), channel worker guard (`channel.worker_guard.idle_timeout` / `max_live_workers`), Codex dispatch mode (`codex.dispatch_mode: inline | sub-agent`), and the spec registry block (`registry.spec.source` + `registry.spec.template`).
- `.atw/spec/` stores the user's project-specific coding conventions and design constraints. When `registry.spec` is set, files are refreshed by `atw update`; local edits surface as "modified by user" conflicts in `.atw/.template-hashes.json`.
- `.atw/tasks/` stores task PRDs, research files, and JSONL context. Tasks form parent/child trees: `task.py create --parent <slug>`, `task.py add-subtask <parent> <child>`, `task.py remove-subtask <parent> <child>`, and `task.py list-context <task>`. `task.py create` rejects a slug already present in `.atw/tasks/archive/**`.
- `.atw/workspace/` stores **deliberately written** developer journals. Raw cross-session dialogue is **not** stored here — it lives on disk under `~/.claude/projects/`, `~/.codex/sessions/`, and `~/.pi/agent/sessions/` and is recovered via `atw mem search|extract|context`. The bundled `atw-session-insight` skill teaches when to reach for `mem`.
- `.atw/agents/{review,implement-agent}.md` are bundled, platform-agnostic channel runtime agent definitions loaded by `atw channel spawn --agent <name>`. Editable; `atw update` backfills missing ones. Editing the per-platform `atw-implement-agent.md` / `atw-review.md` does **not** change channel-runtime worker behavior.
- `~/.atw/channels/<project>/<channel>/events.jsonl` is the channel runtime event log per project per channel. User-owned, file-locked sequence numbering, durable `idempotencyKey` support; never under `.atw/`.
- Bundled multi-file skills (`atw-meta`, `atw-spec-bootstrap`, `atw-session-insight`, `atw-channel`) are auto-dispatched to every platform skill root by `getBundledSkillTemplates()` in `packages/cli/src/templates/common/index.ts`. Dropping a new directory under `packages/cli/src/templates/common/bundled-skills/` (upstream) ships it to every platform on the next `atw update`.
- Platform settings/config files decide which hooks, agents, skills, commands, prompts, and workflows actually run. Reasonix has no settings file — behavior is encoded inside skill frontmatter.
- `.atw/.template-hashes.json` and `.atw/.runtime/` are management/runtime state files. Confirm necessity before editing them.

## Do Not

- Do not treat ATW upstream source code as the default target for local customization.
- Do not modify the global npm install directory or `node_modules/@chinhae/atw-cli` or `node_modules/@chinhae/atw-core` to implement project needs; both packages ship in lockstep.
- Do not overwrite user-modified local files with default templates; check `.atw/.template-hashes.json` first and prefer `.new` sidecar files over destructive overwrites.
- Do not put team-private project rules into any public bundled skill (`atw-meta`, `atw-spec-bootstrap`, `atw-session-insight`, `atw-channel`); put project rules in `.atw/spec/`, a project-local skill, the current task, or the workspace journal — `atw update` will overwrite anything inside a bundled skill directory.
- Do not hand-edit `~/.atw/channels/<project>/<channel>/events.jsonl`; sequence numbers are assigned under a file lock and replay-safe writes go through the `atw channel` CLI or the `@chinhae/atw-core/channel` SDK.
- Do not edit `.claude/agents/atw-implement-agent.md` (or any other per-platform sub-agent file) when the goal is to change channel runtime worker behavior — edit `.atw/agents/<name>.md` instead.
- Do not describe removed or never-shipped mechanisms as current ATW behavior; cross-check against the local `.atw/config.yaml` and the installed CLI's `atw --help` before claiming a knob exists.
